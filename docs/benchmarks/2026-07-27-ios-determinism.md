# 2026-07-27 iOS Determinism Benchmark

This evidence pack answers a narrower question than the timing packs in this
directory: not *how fast* the runner is, but *whether it gives the same answer
twice*. It is a single-tool benchmark on ZMR's own generated fixture, not a
comparison against Maestro, Appium, Detox, or XCTest.

## Result

| Metric | Value |
| --- | --- |
| Scenario | `.zmr/react-native-expo-ios-workflow.json` (17 steps) |
| Platform | iOS simulator |
| Runs | 20 |
| Passed | 20 |
| Failed | 0 |
| Pass rate | 100.00% |
| Distinct event counts | **1** (`45` on every run) |
| Mean duration | 50907 ms |
| Median duration | 50996 ms |
| p95 duration | 51198 ms |
| Min duration | 50249 ms |
| Max duration | 51296 ms |
| Spread (max − min) | 1047 ms (2.1%) |
| Standard deviation | 285 ms |

**The event count is the load-bearing number, not the durations.** All twenty
runs emitted exactly 45 events and reported `traceStatus: passed`. A constant
event count means the runner walked the identical path through the scenario
twenty times — launch, deep link, taps, typing, waits, assertions, snapshots,
trace write. Twenty passes with varying event counts would only show that the
scenario is tolerant; twenty passes with an identical count shows the run is
reproducible.

The 2.1% duration spread is wall-clock noise on a shared machine, and is the
weaker half of this result. Treat p95 as the number to gate on.

## Independent repeat

An earlier 20-run sample the same day, on the same host and build, produced
median 51.2 s, p95 51.5 s, spread 2.1%, and the same `45` event count on every
run. Two independently collected samples agreeing to within ~0.3 s at the median
is a stronger statement than either sample alone.

## Command

Metro must already be serving the app, and must outlive every run. The harness
starts the app fresh before each run, because the scenario types into a profile
form and React keeps that text in component state — without a relaunch, later
runs drift for reasons that have nothing to do with the runner.

```bash
# in the generated app directory
npx expo start --dev-client --port 8081

# in this repository
caffeinate -i ./scripts/determinism-bench.sh \
  --scenario /path/to/app/.zmr/react-native-expo-ios-workflow.json \
  --app-dir /path/to/app \
  --scheme zenoexpodemo \
  --runs 20 \
  --results traces/determinism/results.jsonl
```

`caffeinate` is not optional. An earlier attempt let the host sleep mid-run and
reported durations inflated to twenty minutes.

Sanitized per-run rows: [`2026-07-27-ios-determinism.results.jsonl`](2026-07-27-ios-determinism.results.jsonl).

## Scope — what this does not establish

- **The fixture is ZMR's own generated Expo app, not a third-party app.**
  [`../production-readiness.md`](../production-readiness.md) requires pilot
  evidence from real app teams, and this does not provide it. It shows the runner
  is stable end to end on a known-good app; it does not close the Product Gates
  Before 1.0.
- One host, one Xcode, one simulator, one OS version. No device matrix.
- The scenario passes on every run, so this exercises the success path only. It
  says nothing about how consistently failures are classified.
- Durations are wall-clock on a machine also running Metro, a simulator, and an
  XCTest shim. They are not a performance claim against any other tool.

## Reproducing the failure modes

Three environment faults produced confident, wrong-looking results while
collecting this, all of which the harness now refuses to run through. They are
worth knowing because each one looks like a flaky runner:

| Fault | Signature |
| --- | --- |
| Metro not running | Every run fails, `eventCount` 7–12, varying — reads as flakiness |
| Deep link sent before the dev launcher is ready | App parks on `DEVELOPMENT SERVERS`, every wait times out |
| `zmr` run from outside the app directory | Relative `iosShimPath` does not resolve, no UI tree, `WaitTimeout` with empty `visibleTexts` |

The harness fails fast on the first two: it requires a live bundler before
starting and runs one unmeasured warm-up that must pass before any row is
recorded.
